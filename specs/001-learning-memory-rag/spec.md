## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每日自动沉淀（Priority: P1）

用户（单人开发者）每天晚间执行一次同步，系统自动采集当天在多个 AI 编码工具中的会话素材、git 提交与手动快记，蒸馏为结构化学习条目并入库。用户不写任何额外内容，次日即可查询"我昨天学了什么"。

**Why this priority**: 这是系统存在的理由——零额外成本的自动记忆沉淀。没有它，其余功能都无数据可用。

**Independent Test**: 可用单日真实素材跑通"采集→蒸馏→入库"，第二天能查到当天内容。

**Acceptance Scenarios**:

1. **Given** 当天各工具有会话记录、有手动快记，**When** 用户执行当日同步，**Then** 生成当日原始素材快照文件，且库中出现条目数 > 0、字段齐全（正文/日期/类型/标签/来源/项目/创建时间/溯源/关联）。
2. **Given** 同一日期已同步过一次，**When** 再次执行同日同步，**Then** 库中条目数不变、不产生重复关联（幂等）。
3. **Given** 当天没有任何素材，**When** 执行当日同步，**Then** 正常结束，写出空的原始快照文件（保留重蒸馏基线），不报错。
4. **Given** 某个工具的素材目录已消失，**When** 执行同步，**Then** 同步成功（该来源无操作），日志留有记录，其他来源正常入库。

---

### User Story 2 - 带过滤的语义检索（Priority: P1）

用户以自然语言提问（如"我在 ark 代理上踩过什么坑？上周的"、"最近的报错"），系统按语义检索并支持类型/日期/项目过滤，回答中每条结论附可追溯引用（`[日期] 类型: 摘要`）。

**Why this priority**: 沉淀的价值只有通过检索才能兑现；与 US-1 共同构成最小可用闭环。

**Independent Test**: 入库若干已知条目后，提问与之相关的问题，验证命中、过滤与引用格式。

**Acceptance Scenarios**:

1. **Given** 库中含若干 error 类型条目，**When** 用户带类型过滤提问，**Then** 仅 error 类型参与回答，引用标注日期与类型。
2. **Given** 库中条目跨越多天，**When** 用户限定日期区间提问，**Then** 区间外条目不参与。
3. **Given** 存在与命中条目内容关联但不匹配问句字面的其他条目，**When** 默认检索，**Then** 关联条目作为"关联补充"进入回答上下文；关闭扩展后不再出现。

---

### User Story 3 - 手动快记（Priority: P2）

用户随手记一句话想法（命令行或接口），落到快记文件，随当日素材一起入库。未标类型时默认归为反思类。

**Why this priority**: 碎片想法是会话记录覆盖不到的素材；实现轻，但依赖 US-1 的管道存在。

**Independent Test**: 快记一条内容，执行当日同步后能检索到它。

**Acceptance Scenarios**:

1. **Given** 用户提交一条快记，**When** 当日同步执行，**Then** 该内容以快记来源进入库中，且不经过 LLM 蒸馏（轻处理路径）。

---

### User Story 4 - 采集范围手动选择（Priority: P2）

用户通过交互选择器查看 工具×项目 矩阵（含最近会话日期、估算条数等元信息），勾选纳入采集的工具与项目；选择结果写入纯文本配置，配置文件是唯一事实来源，选择器只是它的编辑器。

**Why this priority**: 采集面需要用户控制（隐私与噪声）；但初装时可先用默认全选，故 P2。

**Independent Test**: 取消勾选某工具后同步，该工具的素材不再被采集。

**Acceptance Scenarios**:

1. **Given** 选择器展示矩阵，**When** 用户取消勾选某工具并保存，**Then** 配置文件更新，后续同步跳过该工具。

---

### User Story 5 - 蒸馏质量校准（Priority: P3）

用户修改蒸馏标准或更换蒸馏模型后，对指定日期重蒸馏，得到新旧条目集的对照差异（新增/消失/改写），确认后整组替换该日条目或丢弃。

**Why this priority**: 质量校准回路——长期价值高，但依赖主流程稳定后才有意义。

**Independent Test**: 修改一处蒸馏标准，对已同步日重蒸馏，差异清单正确反映变更；应用后该日条目被整组替换。

**Acceptance Scenarios**:

1. **Given** 某日已入库且原始快照仍存在，**When** 用户修改蒸馏配置后重蒸馏该日，**Then** 系统输出新旧条目集差异清单（按溯源对齐）。
2. **Given** 差异清单已产出，**When** 用户确认应用，**Then** 该日条目先删后插整组替换，幂等 ID 保证可安全重跑。

---

### User Story 6 - 新工具接入（Priority: P3，扩展性验证）

新的 AI 编码工具出现后，用户按插件模板实现"发现 + 解析"两函数，放入插件目录，无需修改核心代码即被自动注册；插件移除后系统静默继续运行。

**Why this priority**: 产品随时间增减是常态，架构必须预留；v0.1 交付的四个插件已验证架构，PRD v0.7 又一次性把采集面从 4 个扩到 11 个——这本身就是该架构的规模验证（核心零改动）。

**Independent Test**: 按模板新建一个指向任意测试数据的插件，验证被自动发现并能采集。

**Acceptance Scenarios**:

1. **Given** 插件目录中新增一个符合契约的插件，**When** 执行同步，**Then** 无需改动核心代码，新插件素材被采集。
2. **Given** 某插件解析抛出异常，**When** 执行同步，**Then** 仅该来源跳过并记录日志，其余来源正常完成。

### Edge Cases

- 蒸馏模型返回无法解析的结构：重试一次；仍失败则当日蒸馏记为失败，原始快照已落盘可重跑（不产生半成品数据）。
- 蒸馏返回不在类型枚举中的类型：重试一次（prompt 纠正）；仍失败丢弃该条并记录。
- 单日素材异常大：蒸馏前截断至配置上限，并受**每次运行**条数熔断保护（默认 30 条；按运行计、不按自然日累计，v0.7.6 订正）。
- 会话时间戳跨时区：统一折算到用户时区（Asia/Shanghai）后判定归属日。
- 外部服务（嵌入/问答/向量库）不可用：同步以非零码失败退出，已入库部分可安全重跑；检索时给出明确引导提示。
- 手动快记未标类型：默认归为反思；轻处理路径不改类型（需改类型请在快记时标注）。
- 采集插件改名导致条目 ID 变化（`trae` → `trae_work_cn`）：条目 ID 由 `来源|日期|内容哈希` 决定，改来源即换 ID，旧条目会变成孤儿。MUST 先跑一次性迁移脚本（按旧来源捞出 → 按新来源重算 ID → upsert 新点 → 删旧点），再启用新插件；顺序不可颠倒，否则同一素材以两个 ID 并存。迁移脚本 MUST 幂等、可 dry-run，且迁移前后正文哈希集合 MUST 逐一对应（PRD §8）。
- SQLite 源在采集期间被产品占用或不可读：视为该来源当日不可用，按故障隔离跳过并记录，不影响其他来源（PRD NFR-004）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以插件方式组织采集：每个产品一个插件，实现"发现当日素材引用"与"解析为统一中间格式"两个函数，由注册机制自动扫描注册；插件目录消失时 MUST 静默跳过（PRD FR-001）。
- **FR-002**: v0.1 MUST 交付 4 个采集插件：claude-code、codex、kimi-code（原始会话完整解析）与 trae（读取其已蒸馏的记录做轻量转换直接并入，不做二次蒸馏；记录字段到类型枚举的映射由配置驱动，未匹配默认归反思类）（PRD FR-002、FR-013）。**PRD v0.7 起该插件更名为 `trae_work_cn`**（其数据源一直是 `~/.trae-cn`），`trae` 之名转给 `~/.trae`。
- **FR-002a**: 采集面 MUST 扩展到 11 个插件，分为两族（PRD FR-002a）。
  - **A 族 · Claude/JSONL 系**（时间戳与注入物策略逐源不同，MUST NOT 假定可共用解析器）：
    - `qoder` / `qoder_cn`：JSONL，两者 schema 逐字段相同，**MUST 各自实现解析器、MUST NOT 互相 import**（v0.7.1 裁决：长得像不等于可以共用，共用会把两个独立产品的 schema 演进绑死），两边的漂移由一条**跨插件等价性测试**钉住（同一份构造输入分别喂给两个解析器，产出 MUST 逐字段相同）；**时间戳双编码**（消息类 ISO 8601 UTC 字符串、bookkeeping 类 epoch 毫秒），同文件内混排，解析 MUST 先判类型。
    - `workbuddy_ai`：JSONL，CodeBuddy 系 schema，MUST NOT 复用 qoder 解析器；时间戳统一 epoch 毫秒；**正文 MUST 只取 `<user_query>…</user_query>` 内的内容**（实测 116 条 user 记录中仅 47 条为真实输入；判据是 `<user_query>` 标签本身，不是比例），取不到则该记录 MUST 不产生素材。
    - `trae`：与 `trae_work_cn` 同格式同映射规则，仅数据根不同。
  - **B 族 · SQLite 系**（MUST 以 `mode=ro` URI 只读打开，见 FR-011a）：
    - `opencode`：`session_message` 表（`data` 列为 JSON），epoch 毫秒。
    - `zcode`：`message` + `part` 表，epoch 毫秒；MUST 排除 `message.data.synthetic` 为真的记录（实测 343 条 user 消息中 115 条为注入物）。
    - `hermes`：MUST 按 schema 实现；该源当前零真实数据，其验收依据**仅为构造 fixture，未经真实数据验证**，补验前 MUST NOT 据此声称任何验收标准通过。
- **FR-002b**: `~/.workbuddy` 与 `~/.workbuddy-ai` 是同一产品的两个数据根，采集 MUST 只读后者（前者为守护进程 home，无会话数据）（PRD FR-002b、NG-012）。
- **FR-003**: 系统 MUST 采集配置所列仓库的当日 git 提交（PRD FR-003）。
- **FR-004**: 系统 MUST 支持手动快记（命令行与接口共用同一实现），未标类型时默认反思类（PRD FR-004）。
- **FR-005**: 系统 MUST 提供交互式范围选择器，其结果 MUST 写入纯文本配置文件，且配置文件是唯一事实来源（PRD FR-005）。
- **FR-006**: 每日采集结果 MUST 先落盘为统一中间快照，内含本次蒸馏运行元信息（模型、标准版本）（PRD FR-006）。
- **FR-007**: 蒸馏 MUST 按可配置的价值标准执行：纳入/排除信号、保留与丢弃示例、新颖度阈值、每次运行条数上限、挣扎轮次均由配置驱动（PRD FR-007）。
- **FR-008**: 蒸馏 MUST 提取行为证据：同一问题达到配置轮次仍未解决再解决的记录视为高价值信号（PRD FR-008）。
- **FR-009**: 蒸馏 MUST 做新颖度去重：候选条目先与库中已有条目比对相似度，超阈值则跳过或并入（PRD FR-009）。
- **FR-010**: **每次同步运行**的入库条数 MUST 受可配置上限（默认 30）熔断保护；计量单位是**一次运行**，同一天多次运行各自受此上限约束、互不累计（PRD FR-010，v0.7.6 订正）。
- **FR-011**: 蒸馏前 MUST 做正则脱敏（密钥、令牌、密码模式）（PRD FR-011，NFR-001）。
- **FR-011a**: 采集 MUST 保持源目录零写入，SQLite 源尤甚（PRD NFR-001，宪法 V）。
  - 对产品源目录的任何 `sqlite3.connect()` MUST 使用 `file:<path>?mode=ro` URI（普通 `connect()` 会在源目录落 `-wal`/`-shm`/`-journal`）。此约束 MUST 由 `scripts/write_boundary_check.py` 机械拦截，并在 `make gate-selftest` 中有对应的植入违规用例。**注意 `mode=ro` 保证的是「不改 `db` 本身」，不是「绝不落 sidecar」**——sidecar 不存在时只读连接会自己造出 `-wal`/`-shm`（2026-09-26 实测），边界全文见 PRD NFR-001 的「已知边界」。
  - 凭据 MUST 被双向排除：B 族插件 MUST 用**表允许列表**（只读列出的表，而非排除黑名单），A 族插件 MUST 用**路径允许列表**。需排除的表为 `opencode.db` 的 `credential`/`account`/`control_account`；需排除的路径包括 `~/.zcode/v2/credentials*.json`、`~/.hermes/` 下的 `.env` 与 `auth.json`、`~/.workbuddy/connectors/`、`~/.qoder-cn/` 下的 `state.json`。
- **FR-012**: 蒸馏产物超出类型枚举时的处理 MUST 为：重试一次（prompt 纠正），仍失败丢弃该条并记录（PRD FR-012）。
- **FR-013**: 入库 MUST 幂等：条目标识由"来源|日期|内容哈希"确定性生成，重复同步不产生重复数据（PRD FR-014，NFR-003）。
- **FR-014**: 条目 MUST 携带完整溯源：正文、日期、类型、标签、来源、项目、创建时间、溯源引用、蒸馏版本、关联（PRD FR-015）。
- **FR-015**: 类型枚举 MUST 由配置驱动，新增类型零代码迁移（PRD FR-016，NFR-005）。
- **FR-016**: 入库时 MUST 构建关联边：相似度 top-5 中超过阈值（0.75）的建立双向边，单条上限 5；对方已达上限时跳过该方向回填，过程确定性幂等（PRD FR-017）。
- **FR-017**: 检索 MUST 支持语义搜索加类型/日期/项目过滤（PRD FR-018）。
- **FR-018**: 回答 MUST 带引用，每条结论可追溯至日期、类型、摘要与来源（PRD FR-019）。
- **FR-019**: 关联扩展 MUST 可配置（关闭/全量/相似度阈值三模式，默认全量），扩展条目在回答上下文中标记"关联补充"，并支持单次关闭（PRD FR-020、FR-021）。
- **FR-020**: 原始快照保留期 MUST 可配置（默认 90 天，可设永久），到期由同步清理（PRD FR-022）。
- **FR-021**: 系统 MUST 支持重蒸馏对照：新旧条目按"共享溯源引用且文本相似度 ≥0.85"配对，配对有差异记改写、仅新集合记新增、仅旧集合记消失；应用后整组替换该日条目（PRD FR-023）。
- **FR-022**: 同步 MUST 以纯命令行形式可运行，不依赖接口进程存活（PRD FR-025）。
- **FR-023**: 接口薄壳 MUST 提供健康检查、快记、后台同步与状态查询、检索问答四类端点，路由层不含业务逻辑（PRD FR-024）。

### Key Entities

- **学习条目（Learning Entry）**: 系统的核心数据单元——一条蒸馏后的知识点/错误/想法/反思。属性：正文、日期、类型（可扩展枚举）、标签、来源（会话/提交/快记）、项目、创建时间、溯源引用（source_refs）、蒸馏版本（distill_version）、关联（related）。由幂等 ID 标识。
- **原始素材快照（Raw Snapshot）**: 某日全部采集素材的统一格式中间文件，含蒸馏运行元信息。重蒸馏的输入与审计基线，有保留期。
- **采集插件（Collector Plugin）**: 面向单一产品的采集单元，实现发现与解析两函数，由注册机制自动管理。分 raw（需蒸馏）与 pre-summarized（轻转换）两类素材路径。
- **关联（Relation）: 两条学习条目间的双向语义关联边，入库时按相似度构建，检索时可一跳扩展。
- **配置（Configuration）**: 类型枚举、蒸馏标准、检索参数、采集范围、保留策略的唯一事实来源（纯文本，入库 git，不含密钥）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用当日真实素材完成一次端到端同步后，库中出现字段齐全的条目且可被检索（PRD AC-002）。
- **SC-002**: 同一日期重复同步，库中条目数与关联边数不变（PRD AC-003）。
- **SC-003**: 带类型与日期过滤的提问，**主检索结果**仅含符合过滤的条目，且每条结论带引用（PRD AC-004）；关联补充条目不受该过滤约束、单独标记（PRD FR-020）。
- **SC-004**: 关联扩展默认开启并正确标记；单次关闭后扩展条目消失（PRD AC-005）。
- **SC-005**: 任一采集来源目录消失时，同步仍成功完成其余来源（PRD AC-006）。
- **SC-006**: 范围选择器修改配置后，后续同步按新范围采集（PRD AC-007）。
- **SC-007**: 保留期到期后原始快照被清理，库中条目不受影响（PRD AC-008）。
- **SC-008**: 过去日期可补跑同步，行为与当日一致（PRD AC-009）。
- **SC-009**: 修改蒸馏标准后重蒸馏指定日，差异清单正确；应用后该日条目整组替换（PRD AC-010）。
- **SC-010**: 配置中新增一个类型后，无需改代码即被蒸馏识别（PRD AC-011）。
- **SC-011**: 典型素材量的当日同步全程 ≤ 5 分钟（PRD NFR-006）。**计时 MUST 按「天」不按「源」**（v0.7.3 订正：真实 sync 把当天全源素材合并后统一分批，成本不按源可加，逐源计时从原理上测不出总预算）——单源耗时降为**诊断指标**，可记录但不作验收尺子。已实测：2026-09-26 最忙日 09-25（1,928,545 字符 / 18 批 / 3 轮）全源端到端 **248.7s / 300s（83%）**，未突破；采样面仅 1 天、无 run-to-run 方差样本，余量不保证次次够。当日计时逼近 300s 即触发 PRD §9 风险表中的处置顺序——**不得在无实测的情况下放宽预算**。
- **SC-012**: 备份等于复制单个数据目录；迁移等于复制三个目录（PRD NFR-007）。
- **SC-013**: 植入伪造密钥的快记经同步后，库中条目、原始快照与日志均不出现该密钥串（PRD AC-012）。
- **SC-014**: 配置外类型的蒸馏条目被重试一次后丢弃并留日志，其余条目正常入库（PRD AC-013）。
- **SC-015**: 条数上限生效：**该次运行**恰好入库上限数量、日志含熔断记录、同步正常结束（PRD AC-014）；上限按运行计——同一天连跑两次，第二次不因第一次已入满而被压到 0。
- **SC-016**: 基础设施启动后连通性可验证：向量库管理界面可访问，健康检查端点返回各组件状态（PRD AC-001）。
- **SC-017**: 注册的采集插件数为 11；每个新增源在有数据的日期单独同步时素材非空**且结局可判**（`distill_run.per_source` 给蒸馏侧的 `materials`/`kept`、`sync` 汇总的 `skipped_by_source` 给入库侧被新颖度拦掉的条数；「有素材 → 0 点」必须能判因）——v0.7.9：本条只声明观测对象，验证方法见 `quickstart.md`，不再把「单独 `make sync D=<date>`」写死为唯一路径，且注入物被排除（zcode 的 `synthetic` 记录不入库、workbuddy_ai 条目正文只含 `<user_query>` 内容）。hermes 因库为空不适用本项（PRD AC-015）。**v0.7.7 订正**：原文漏写「入库成功」——PRD AC-015 要的是**两半**，spec 转录时只剩「素材非空且注入物被排除」，`tasks.md` 的 AC-015 证据随即也只记了前半句，「入库成功」因此长期无人核（详见 PRD §13 v0.7.7）。
- **SC-018**: 改名迁移脚本 dry-run 列出 9 条待改写条目；应用后旧来源条目数为 0、新来源条目数与之一致且正文哈希逐一对应、总数不变，重复应用无副作用（PRD AC-016）。迁移判据是 **ref 路径**（旧数据在 `~/.trae-cn/`）而非 source 名——v0.7.1 后 `trae` 这名字被新插件合法复用；「重复应用无副作用」由**默认拒跑 + `--force` 只迁旧路径**来保证，故重跑会以退出码 2 停下而非静默重写。
- **SC-019**: 任一 SQLite 插件跑完后源目录无 `-wal`/`-shm`/`-journal` 新增（**在产品运行期间成立**；sidecar 已被产品删除时 `mode=ro` 会重建，属 NFR-001 已知边界，须记录实测前置状态）；`write_boundary_check` 对非 `mode=ro` 的 `sqlite3.connect()` 判红（PRD AC-017）。

## Assumptions

- 各 AI 编码工具的素材路径与格式可能随其版本漂移，影响被隔离在单个插件的解析层内（PRD §9 假设）。
- 嵌入与蒸馏模型的确切可用标识在安装配置阶段以真实调用验证（PRD §9 假设）。
- 本项目尚无 git 仓库（PRD 未要求初始化；如后续需要，属环境决策，由用户决定时机）。
- 范围边界：本 spec 不含任何 PRD §3.2 NG-001~012 所列能力（NG-010 已于 PRD v0.7 撤销），需求参见 Out of Scope。
- 素材中可能含敏感信息（密钥等），系统按 FR-011 在蒸馏前脱敏；素材送往蒸馏服务的数据流向与用户现有工具使用方式一致（PRD §9 风险）。
