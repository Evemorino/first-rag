## ADR-c1 蒸馏并行化：`distill.parallel_workers`（默认 8）

**现状**：`src/distill.py:309-310` 用 `ThreadPoolExecutor(max_workers=workers)` 并发跑各批，
用 `pool.map` 保序（完成顺序不定、合并结果与串行一致，`_cap_entries` 取前 N 条不会裁错）；
`config/schema.json:35` = 8；`src/config.py:119` 校验 ≥1。

**备选**

| 方案 | 当时为何没选 |
|---|---|
| 保持串行 | 09-24 实测 983s，超 300s 预算 3.3×（tasks.md T031） |
| 少分几批（调大 `batch_max_chars`） | 与「输出会被服务端截断」直接冲突 —— 批越大输出越长越容易断 |
| 多进程 / 异步 | 瓶颈是等 HTTP 返回（纯 I/O），线程够用；多进程白付序列化成本 |
| workers 提到 16+ | 未实测；方舟侧限流（429）没有采样 |

**证据**：同一天（09-24，57 素材 / 13 批）三次对照 —— 串行 **983s** → 4 workers **338s**
→ 8 workers **215.9s**（300s 预算用掉 72%）。4 workers 时 13 批要跑 4 轮、末轮 1 批空转
3 个 worker，这是 338s 收不进去的直接原因。

**可逆性**：配置项。改小 1 行配置；删键则 `src/distill.py:292` 的 `.get(..., 4)` 兜底为 4。
代码不用动。

**待你判断**

- 8 这个数是怎么定的？（现仓里只有「8 workers 实测 215.9s」这一个点，没有 16 或 6 的对照）
- 末轮空转是批数取模 worker 数的固有损失。这属于「配置得不对」还是「可以接受」？
- 并发上去了，方舟的限流/计费策略有没有边界？现在是**未知**，不是「没问题」。

## ADR-c2 按输出切批：`distill.batch_max_chars`（默认 120000）

**现状**：`src/distill_batches.py` 的 `split_for_batches` 贪婪装箱（按素材原顺序累加，
超预算另起一批；单条自身超预算给它独立一批而不丢弃）；`src/distill.py:277-291` 按批调用；
`config/schema.json:34` = 120000。

**备选**

| 方案 | 当时为何没选 |
|---|---|
| 加大 `max_tokens` | 无关：断的是**服务端 completion 上限**，不是请求参数。实测 `max_tokens=30` 也一样慢/断（T030） |
| 靠 `_parse_or_retry` 重试 | 重试是**原样再发**，同一处再断一次，整天 0 条入库 |
| 按素材**条数**切批 | 尺寸极不均（一条会话可达 200000 字符），字符数才是决定量 |
| 流式收输出再拼 JSON | 未走；解析半截 JSON 的成本没评估 |

**证据**：09-18 断在 **6894 字符 / 6865 tokens**、`finish_reason='length'`；而输入大 5.7 倍的
09-23（1.33M 字符）一次就过 —— 决定成败的是**输出**长度，不是输入长度（这正是这个决策
反直觉、值得留痕的地方）。

**可逆性**：配置项，改 1 个数字。

**待你判断**

- **120000 这个数在仓库里没有推导过程**（我把 `src/`、README、PRD、specs 都搜了）。
  它相对实测断点（~6.9k 输出）的余量是「宽松到不会断」，还是「刚好」？这个数你认不认？
- 切批会让 `source_refs` 只能引用本批（`src/distill.py:283`），跨批的关联在蒸馏期就断了。
  这是可接受的代价，还是应该在 ADR 里显式记为副作用？

## ADR-c3 思维链默认关：`retrieval.disable_thinking`（默认 true），但**蒸馏保持开**

**现状**：`src/ask.py:153` 读配置传 `thinking=not retrieval["disable_thinking"]`；
`src/ark_client.py:71-72` 在 `thinking=False` 时加 `extra_body={"thinking":{"type":"disabled"}}`；
`config/schema.json:40` = true。注意 `ark_client.chat` 的默认 `thinking=True` 语义是
**「不传这个键、让服务端保持原样」**，不是「显式打开」（`src/ark_client.py:63-65`）。

**备选**

| 方案 | 当时为何没选 |
|---|---|
| 调低 `max_tokens` | 实测无效：`max_tokens=30` 仍 38s、200 要 43.5s（T030） |
| 靠流式掩盖延迟 | 首字仍卡在思考上（33.4s），只是感知稍好 |
| 换模型 | 未走 |
| 全局关（含蒸馏） | 蒸馏关掉后同批条目 **9 → 28 条**，质量/数量差异未经评估 → 只对 ask 关（tasks.md T030） |

**证据**：TTFT 33.4s → **1.6–4.1s**；整轮 71.6s → **5.91s**；流式首字 **0.7s**。
另有一条归因教训：先前把 71.6s 记成「模型 TTFT 天生 20–40s」是**误判**，真因是 doubao 系
**默认跑思维链**（响应带 `reasoning_content`）。

**可逆性**：配置项，改 1 个布尔值。

**待你判断**

- 「蒸馏不关 thinking」的理由是「条目 9→28，质量差异未经评估」。**这个评估做不做？**
  不做的话等于把「质量」永久悬置 —— 而 9→28 的差异是 3 倍量级，很难说与质量无关。
- 「默认 true（关）」与「默认 false（开）」谁是安全默认？现在关它是拿**回答质量**换延迟，
  这个交换你做的时候知道吗（当时是性能问题驱动的）？

## ADR-c4 SQLite 源一律 `file:…?mode=ro` + `uri=True`

**现状**：三个 B 族插件各自 `_query`：`src/plugins/zcode/__init__.py:75`、
`src/plugins/hermes/__init__.py:78`、`src/plugins/opencode/__init__.py:57`；
凭据按路径与表双向排除（各有 `ALLOWED_TABLES`：zcode 2 表、hermes 2 表、opencode 1 表）。
门禁：`scripts/write_boundary_check.py`（规则在 `--list` 的「硬法」段）。

**备选**

| 方案 | 当时为何没选 |
|---|---|
| 普通 `connect()` | 在源目录落 `-wal`/`-shm`/`-journal` = 写入 = 违宪 V，且违规不可恢复 |
| `immutable=1` | 零落盘，但**忽略 `-wal`** → 静默读到过期数据（README:535 明确不采用） |
| **先复制库到 tmp 再读** | **现有记录里我没找到它的评估** —— 见下 |

**证据**：对照实验（干净 WAL 库，目录里只有 `t.db`）：`connect("file:…?mode=ro", uri=True)`
打开后目录变成 `['t.db','t.db-shm','t.db-wal']` —— 只读连接在 sidecar 不存在时**自己造**
它们。推论两条：① 源目录不可写时插件打不开库，只能降级为空数据（表现为「该源当天无素材」
而非报错，由 NFR-004 的 warning 兜住）；② AC-017① 从「文件列表逐一致」降级为
「**db 文件逐字节不变**，sidecar 的 mtime 变化属已知边界」。

**可逆性**：改 3 处 `connect` 调用 + 门禁规则 + 3 组插件测试。改动面小但都在宪法 V 的监管下。

**待你判断**

- 「复制到 tmp 再读」是**唯一能同时做到零落盘 + 读最新**的路子。它没有被采纳的原因是
  什么？（拷贝成本？源库运行中的一致性？）如果这条从没被评估过，那 ADR-c4 的「理由」
  就少了一个真正的对手 —— 记下来比不记好。
- 接受 sidecar mtime 变化，等于把「产品源目录文件永不变化」这个强承诺降级为
  「db 文件不变」。**这个降级你认不认？**认了才该写进 ADR，而不是只写进 NFR-001 的边界。

## ADR-c5 快照写保护：三条并列拒写 + `ALLOW_SHRINK=1` 明路

**现状**：`src/collect.py:206-292`（`save_snapshot` / `_existing_snapshot`），
拒写判据 = ①条数变少 ②**有来源从盘上消失** ③**快照结构读不出来**；
`src/sync.py:116-166` 接线，`Makefile:28-30` 暴露 `ALLOW_SHRINK=1`。

**备选**

| 方案 | 当时为何没选 |
|---|---|
| 裸覆写（原状） | 已**实际造成损失**：单源验证跑覆盖多源快照，09-18/09-23 靠迁移备份才还原 |
| 一刀切禁止覆盖 | 窄 scope 重跑（合法操作）会被误伤，需要留明路 |
| 只比条数（v0.7.4 第一版） | 「同数量换来源」拦不住（`{trae:1}` 覆盖 `{claude_code:1}`），v0.7.8 关掉 |
| **写前先备份、再覆盖** | 未走 —— 见下 |

**证据**：v0.7.4 事故（5 天快照被覆盖，仅 09-18/09-23 有备份可还原，09-21/22/24/25/26
**不可恢复**）；v0.7.8 变异检验：`save_snapshot` + `_existing_snapshot` 的 58 条存活里
逻辑类 13 条，**13 条全部落在未改动的行上**，新增解析逻辑的逻辑类存活 **0**。
代价如实记录：错误信息的散文带来 ~24 条新存活，**变异分数 89.6% → 88.6%**
（分母 2052 → 2107）。同一轮逻辑覆盖是**上升**的。

**可逆性**：改代码 + 门禁 + 一批测试。是这批决策里最难回退的一个。

**待你判断**

- 「拒写 + 人显式开 `ALLOW_SHRINK`」 vs 「先备份再覆盖」：后者能让人不假思索地重跑，
  但要付清理策略（备份存哪、留多久、谁删）。**你更怕哪一种失败** —— 是「挡了一次合法操作」
  还是「又静默弄丢一份基线」？
- 已知代价「错误信息说清楚 → 变异分数下降」你接受吗？（README 分诊表已标为已知且接受，
  但那是**我**标的裁语 —— 该由你确认一次。）
- 这条 ADR 与宪法 V 的写入边界（`WRITE_SITES` 登记 + `only_from` 钉调用方）是同一件事的
  两面：要不要在 ADR 里写明「守卫的完备性由变异测试守，不由覆盖率守」？

## ADR-c6 迁移判据用 ref **路径**，不用 source 名

**现状**：`scripts/migrate_trae_source.py` —— `is_old_trae_ref()` 只认
`~/.trae-cn/memory/` 前缀（:109-116）；`plan_points` 要求 `source_refs` **全部**落在旧目录
（:131，混合/空/指向新目录一律排除 —— fail-safe：证明不了就不动）；`relabel_snapshot`
同判据看 `ref`（:199）；`foreign_refs()` 汇总「挂旧名、ref 却在新目录」的条目（:134-160）；
发现异类时 `main` **默认拒跑**（退出码 2，:373-385）。目录常量取自插件
（`OLD_MEMORY_DIR = trae_work_cn.MEMORY_DIR`，:82 —— 宪法 I：不另抄一份常量）。

**备选**

| 方案 | 当时为何没选 |
|---|---|
| 只看 `source == "trae"`（原版） | v0.7.1 起 `trae` 名被**新插件**（读 `~/.trae/`）合法复用 → 会把新插件素材错标成 `trae_work_cn`，**且不报错** |
| 加一个「迁移已完成」的标记文件 | 又一个状态文件；且不解决「新旧数据混在同一 source 名下」这个真问题 |
| 只迁 Qdrant、不管快照 | 日后 `make redistill` 会照快照把旧 source 写回库里 —— 迁移被无声撤销 |

**证据**：2026-09-26 发现 `--dry-run` 仍报「待改 1 个文件 / 2 条素材（09-21）」，而其 `ref`
指向 **`~/.trae/memory/…`** —— 是新 `trae` 插件的**合法数据**。SC-018 的「重复应用无副作用」
因此失效（它当初成立只因那时没有别的数据叫 `trae`）。

**可逆性**：一次性脚本、已执行完。改动只在「有人回头重跑它」时才有影响，故风险很低。

**待你判断**

- 一个**跑一次就完**的脚本，值不值得 fail-safe 判据 + 全量备份 + 退出码 2 这套投入？
  换句话说：一次性工具的健壮性，和长期工具的健壮性，用同一把尺子吗？
- 「迁移前先落全量状态到 `data/migrations/`」（含向量）现在是一份**没有过期策略**的备份。
  留还是清？（这条与 ADR-c5 的备份策略是同一个问题。）

## 没进这 6 条、但可能够格的边界候选

以下几条同样是实施期做的取舍，T067 没点名。列出来供你裁决要不要一并写：

1. **计时口径按「天」不按「源」**（NFR-006，v0.7.3）—— 理由：真实 sync 把当天全源素材
   合并后统一分批，成本不按源可加，逐源计时从原理上测不出总预算；单源耗时降为诊断指标。
   证据：最忙日 09-25（1,928,545 字符 / 18 批 / 3 轮）端到端 **248.7s / 300s（83%）**，
   采样面仅 1 天、无 run-to-run 方差样本。
2. **`max_entries_per_day` 键名不改**（v0.7.6）—— 理由：`rubric_hash` 是 schema 文本的哈希，
   改名会让全部既有条目的 `distill_version` 与重蒸馏比对基准一起失配，代价大于名字带来的困惑。
   代价：名字说「每日」、行为是「每次运行」。
3. **变异分数为「错误信息写清楚」让路**（v0.7.8）—— 见 ADR-c5 的待判断项。
4. **本项目自己的 README 基线数字无门禁**（2026-09-26 一天内漂了两次：788 → 800、
   90.5% → 90.6%，随后 832 → 834、90.6% → 90.7%、239 → 241 个函数 —— 两次都不是
   代码变差，只是没人告诉 README）—— 是补一个校验脚本，还是继续靠「手写 + 自述无门禁」？

## 格式：ADR 怎么写

现有 ADR-1…11 是**三列摘要表**（决策 + 一句话理由），信息密度在「一行」。上面 6 条的
备选/证据/开放问题塞不进三列。所以你至少要决定：

- **格式**：继续一行式摘要（信息丢得多，但和前 11 条一致），还是每条一个短文件
  （`docs/adr/NNNN-title.md`，含 Status / Context / Decision / Alternatives / Consequences）？
- **放哪**：`docs/adr/`（仓库里还没有 `docs/`），还是 PRD §7 表继续加行？
- **ADR 编号**：从 ADR-12 续，还是另起 `ADR-001`（markdown ADR 惯例）？

**2026-09-26 已定（按建议执行）**：格式走 `docs/adr/NNNN-title.md`，编号**从 ADR-12 续**
（保持一条序列，PRD §7 的 ADR-1…11 不动）。ADR-c2 / c3 / c5 已按此落成
`docs/adr/0012-batch-by-output.md`、`0013-thinking-off-for-ask.md`、
`0014-snapshot-write-protection.md` —— 背景 / 备选 / 证据 / 可逆性已填满，`## 决策` 段留空
待写、状态 Proposed；c1 / c4 / c6 三条结论定了之后回 PRD §7 各加一行摘要，不单独建文件。
目录说明见 `docs/adr/README.md`。

上面每条的「待你判断」就是你需要填的空。
