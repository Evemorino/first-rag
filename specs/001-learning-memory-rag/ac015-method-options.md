2. **09-21 / 09-22 已是单源快照**（09-21 `trae` 2 条、09-22 `trae_work_cn` 58 条，

3. **09-24 / 09-26 是探针产物，不是失败**：两份都是 `distill_run.status = "noop"`，
   按 v0.7.7 的订正，写它们的是**同一进程内的五次 `gather()` 调用**（不持锁、不蒸馏），
   所以 `noop` 应读作「蒸馏从未被调用」。
4. **`zcode` / `workbuddy_ai` / `hermes` / `opencode` 在现存任何快照里都没有素材**
   → 要验这 4 个源的采集，**必然要重新采集一次**，也就必然要落一份快照（除非走不落盘
   路径）。

### 还有一条，它同时否定两个方案的隐含前提

**「素材非空」推不出「入库成功」，而且不可分辨。** `qoder` 就是活例：09-25 的快照里有
它 1 条素材、当日 `distill_run = ok / doubao-seed-2.1-lite`，但库内 `qoder` 点数是 **0**。

单条素材被蒸馏按 rubric 判为低价值（或被新颖度去重拦掉）就会 0 条入库 —— 结果与
「入库路径坏了」**在观测上完全一样**。所以「挑一天单独跑，看该源有没有入库」这个方法，
在**低价值素材的日子上给不出判据**：它既可能因为源坏了而 0，也可能因为源是好的、
只是这天没产出值得记的东西而 0。

## 4. 方案 ①：改方法 —— 验「素材」走不落盘路径，验「入库」走一次全源 sync

**前置实现**：给 `gather` 加不落盘模式（或把落盘上移到 `sync.run`）。

**改动面（本轮实测的调用点）**

| 位置 | 内容 |
|---|---|
| `src/collect.py:57-91` | `gather` 定义，现在结尾无条件 `save_snapshot` |
| `src/sync.py:124` | **唯一的生产调用点** |
| `src/distill.py:180` / `:318` | **`distill` 自己也调 `save_snapshot`** —— 落盘若上移，这两处要一起理顺（终态 `ok`/`noop`/`failed` 是 distill 写的） |
| 测试 15 处 | `collect.gather(` 调用：test_collect 12、test_scope 2、test_plugin_extension 1 |
| `scripts/write_boundary_check.py` | 登记项「`src/collect.py:save_snapshot` -> `data/raw/<day>.json`」必须同步（写入点位移＝门禁红），且 `only_from` 那套钉调用方的机制会跟着变 |

**两个容易漏的细节**

- **锁的范围**：`sync.run` 的 `with _lock(...)` 现在包着 gather→distill→ingest→cleanup
  （`src/sync.py:123-127`）。今天的落盘在 `gather` 内、天然在锁内；落盘上移后**必须仍写在
  锁内**，否则会出现「同一台机器两个 sync 并发写同一份快照」。
- **契约位移**：`collect.gather` 现在的 docstring 明写 persist 属 FR-006（即 gather 就是
  落盘的那条路）。改成不落盘后，得有人接手「谁负责持久化」这条契约，否则它会漂。

**性质**：这是一次**行为变更**（写入点的语义变了），按仓库规矩要走变更控制
（PRD 版本 + §13 + tasks 记录 + 受影响门禁重跑），不是「顺手改个测试」。

**好处**：验证从此不写 `data/raw/`；顺带得到「只读采集探针」这个能力，将来做回填/勘察
都能用。**代价**：一次行为变更 + 门禁登记 + 15 处测试 + 门禁规则重跑。

## 5. 方案 ②：方法保留（单源跑一天），只把「先复制 `data/raw/` 再验证」写进流程

**代码改动**：0。

**流程**：`cp -r data/raw <tmp>` → 单源跑 → 还原。

**今天的守卫会直接拦你**：多源日做单源跑 = 素材数变少 → `SnapshotShrinkError`
（写保护已上线）。所以要么 `ALLOW_SHRINK=1`（**等于在验证时把守卫关一次**），要么复制还原。

**残留风险（未根除）**

- 靠人记得。没有门禁盯「这次验证有没有破坏基线」—— 已出过一次事，靠的是事后发现。
- 进程崩在「已覆盖、未还原」的窗口里，需要人工恢复（复制件就是唯一退路）。
- `ALLOW_SHRINK=1` 的语义是「我确认这次削减是有意的」，拿它跑验证是**语义借用**：
  削减并不是有意的。

**它无法解决的两件事**（都是 §3 的发现）

- 对 `zcode` / `workbuddy_ai` / `hermes` / `opencode`：没有现存素材 → 必然要一次新采集
  → 仍然要落快照。
- 对「低价值丢弃 vs 入库坏了」：仍然不可分辨（`qoder` 的例子）。

**两方案都得付的代价**：单源跑仍会往真库 upsert 点。验的就是入库，这条躲不掉 ——
差别只在于要不要同时动 `data/raw/`。

2. 愿不愿意用「一次行为变更」换掉「一个永久要靠人记得的流程」？（方案① 的本质）

### 8.2 `quickstart.md` 的方法段（草案，可直接抄）

> ### 验一个采集源是否真的通
>
> 分两种情形，**共同前提**：`make sync` 会往**真库** upsert 点，这部分**不可还原**（验的就是
> 入库）；下面这套只保护 `data/raw/` 这份**重放基线**。
>
> **A. 该源在现存快照里有素材**（`claude_code` / `codex` / `kimi_code` / `trae` / `trae_work_cn` /
> `qoder` / `qoder_cn` —— 见 §2）：备份 → 单源跑 → 还原。
>
> ```sh
> DAY=2026-09-25
> ls -l config/scope.json 2>/dev/null || echo "0) 当前无 scope.json（= 全源采集），收尾要删回这个状态"
> BK=$(mktemp -d); rsync -a data/raw/ "$BK/raw/"      # 1) 备份基线（唯一退路）
> test -n "$(ls -A "$BK/raw")" || echo "备份为空，停手"
> make scope                                          # 2) 人显式操作：n → t <源> → s
> make sync D=$DAY                                    # 3) 跑
> ls -l data/raw/$DAY.json                            # 4) 看现场（素材数/来源/status）
> rsync -a --delete "$BK/raw/" data/raw/              # 5) 还原（含删除本次新增的快照）
> diff -r "$BK/raw" data/raw && echo "raw 已还原"     # 6) 核对，必须无差异
> rm -f config/scope.json                             # 7) 仅当第 0 步显示原本没有它
> rm -rf "$BK"
> ```
>
> **B. 该源在任何现存快照里都没有素材**（`zcode` / `workbuddy_ai` / `hermes` / `opencode` ——
> 见 §3 第 4 条）：必然要一次**新采集**，同样先做 A 的 1–2 步；区别是这个源当天**没有**基线
> 可保护，跑到哪一天就新增哪一份快照，跑完按第 5–7 步还原即可。
>
> **三条不要**：不要用 `ALLOW_SHRINK=1` 做验证（那是「我承认这次削减」的语义，不是在验证）；
> 不要在**多源日**上做单源跑还不备份（v0.7.4 事故就是这么发生的）；不要把「库内 0 点」直接
> 读成「入库坏了」（§3 末条：先看 `distill_run.per_source` 的计数）。

**已演练（2026-09-26，只碰 `data/raw/` 与系统 tmp）**：`rsync -a` 备份 → 改前 md5 → 用
`rsync -a --delete` 还原 → `diff -r` 无差异、md5 前后一致（`data/raw/2026-09-25.json` =
`03fa95c0957b3b3c0a088fc6b341d0d4`），7 份快照一份不多一份不少。**未演练的是第 2–3 步**
（`make scope` 与 `make sync`）—— 那两步会写 `config/scope.json` 与真库，按宪法 V 只能由人
显式触发，留给你自己跑。

### 8.3 ② 需要的最小实现（草案）

- **字段**：`distill_run` 增 `per_source`，形状 `{"<source>": {"materials": n, "kept": n,
  "skipped_novelty": n, "dropped_unknown_type": n, "dropped_invalid": n, "capped": n}}`。
  计数来源现成：`src/distill_candidates.py` 已经分成「可用 / 待重试」两堆，熔断在
  `_cap_entries`，逐源的素材数在 `DayRaw.materials` 里。
- **落点**：`src/distill.py:_finish`（三个出口都要带上）+ 四处调用
  （`:330` noop / `:341` direct / `:353` ok / `:356` failed）。
- **一个必须先定的时机问题**：`_finish` 里的 `save_snapshot` 发生在蒸馏内、
  **早于** `ingest.upsert`（`src/sync.py:123-127`）。所以快照装得下**蒸馏侧**的
  kept/丢弃计数，装不下**入库侧**的 `upserted` —— 后者今天只出现在 `sync.run` 的日志汇总
  （`entries_by_source`）。两条路：
  - **(a) 只做蒸馏侧**：无新写入点、不动落盘位置，改动最小；「入库成功」继续看 `sync` 日志。
  - **(b) 落盘上移**到 `sync.run`，一次写入「蒸馏 + 入库」两段 —— 这与 §4 方案①的第 3 步
    （`gather` 不落盘）天然合并，但要一起付写入点登记 + 15 处测试 + 锁范围的成本。
  **建议**：分步就 (a)，一次做到底就 (b)；**别做两遍**（先 (a) 再 (b) 等于同一处字段改两次、
  两次门禁）。
- **可机械验证**：新字段有单测；给一条「低价值被丢」的夹具，断言 `kept = 0` 且
  `skipped_novelty`/`dropped_*` 能唯一判因。

### 8.4 不把第 3 步（`gather` 不落盘）并进 8.3(a) 的理由

`gather` 的落盘是 FR-006 的契约（`src/collect.py:91` docstring 明写），动它要同时理顺
`src/distill.py:180`/`:318` 两处 `save_snapshot`、`sync.run` 的锁范围（今天落盘天然在锁内）、
以及写入边界登记项的 `only_from`。它换来的收益是「采集验证零落盘」；而 v0.7.8 已把最危险的
覆盖（多源 → 单源）拦住了，剩下的是「同数量 + 同来源集合但内容不同」这种窄缝。所以它是
**独立的一次行为变更**，值不值得做见 §7 第 2 条 —— 不该被 8.3(a) 顺带捎上。

## 9. T083 的落地设计（2026-09-26 复核：成本比 §4 估的低得多，待批准）

§7 第 2 条问「值不值得用一次行为变更换掉一个靠人记得的流程」，第 3 条问「落盘归谁」。
第 3 条有明确答案，而且复核后**§4 那张成本表有一半不成立** —— 先把量准，你再判值不值。

### 9.1 推荐：`gather` 加 `persist: bool = True`，落盘**不搬家**

```python
def gather(day, scope=None, *, allow_shrink=False, persist=True):
    ...
    if persist:
        save_snapshot(day_raw, allow_shrink=allow_shrink)
```

- **为什么不把落盘上移到 `sync.run`**：`distill` 自己也写同一份快照（终态 `ok`/`failed`
  由它算出来，`src/distill.py:207`、`:345`），上移就要把「谁写快照」拆到三个调用点重排。
  加开关的改动面小一个量级，FR-006 的契约（快照由 collect 写）也不动。
- **为什么不选 §5 的「先复制再还原」**：那条把 `ALLOW_SHRINK=1` 变成验收流程里的常规
  旁路，且仍然靠人记得。
