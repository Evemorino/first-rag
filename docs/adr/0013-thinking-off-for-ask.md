# ADR-13 思维链默认关，但**只对 ask 关**：`retrieval.disable_thinking`

- **状态**：**Accepted（2026-09-27 用户裁定）**（LG-005：结论由用户写，AI 只给素材与选项；
  问答清单与逐题答案见 `notes/decision-sheet.md`）
- **日期**：2026-09-26
- **素材**：`specs/001-learning-memory-rag/adr-candidates.md` 的 ADR-c3（AI 整理，2026-09-26）
- **后续评估**：决策第 1 条的质量对照已执行（2026-09-27，`tasks.md` **T086**），
  读数与"未复现的那次观察"见「评估记录（T086）」；**质量定性已于 2026-09-28 由用户裁定**
  （采用决策清单的倾向项 A，见文末「质量定性（2026-09-28 用户裁定）」）
- **实施位置**：`src/ask.py` 读配置传 `thinking=not retrieval["disable_thinking"]`；
  `src/ark_client.py` 在 `thinking=False` 时加 `extra_body={"thinking":{"type":"disabled"}}`；
  `config/schema.json` 的 `retrieval.disable_thinking`（默认 true）

## 背景

doubao 系模型**默认跑思维链**，问答因此目测"很慢"。先前的归因是"模型 TTFT 天生
20–40s"——**那是误判**，真因是思维链（响应里带 `reasoning_content`）。
`ark_client.chat` 的默认 `thinking=True` 语义是"**不传这个键、让服务端保持原样**"，
不是"显式打开"。

## 备选与被否的理由

| 方案 | 当时为何没选 |
|---|---|
| 调低 `max_tokens` | 实测无效：`max_tokens=30` 仍 38s，200 要 43.5s |
| 靠流式掩盖延迟 | 首字仍卡在思考上（33.4s），只是感知稍好 |
| 换模型 | 未走 |
| **全局关（含蒸馏）** | 当时现场看到蒸馏关掉后同批条目 **9 → 28 条**（一次观察，**后来未复现**）→ 只对 ask 关 |

## 证据

- TTFT 33.4s → **1.6–4.1s**；整轮 71.6s → **5.91s**；流式首字 **0.7s**。
- 归因教训：把 71.6s 记成"模型天生慢"是误判，真因是思维链 —— 这条比数字本身更值得留。

## 后果与可逆性

- **可逆性**：配置项，改 1 个布尔值。
- **代价与其定性**：关思维链是拿**回答质量**换延迟，而这个交换当时是性能问题驱动的，
  没做质量对照。蒸馏侧的那一半已由 `T086` 补上读数、并于 2026-09-28 定性结案
  （「已评估：无证据显示 OFF 有质量退化」，见文末）；ask 侧靠响应里的引用列表自查，
  **未做**对照 —— 这条边界原样保留。

## 决策

**用户 2026-09-27 裁定（LG-005：结论由用户写；问答清单见 `notes/decision-sheet.md`）。**

1. **「蒸馏不关 thinking」的质量对照：已执行（2026-09-27），读数见「评估记录（T086）」；
   「可接受 / 不可接受」的定性已由用户于 2026-09-28 裁定为「无证据显示 OFF 有质量退化」
   （见文末「质量定性（2026-09-28 用户裁定）」，LG-005）。** 评估之前本条把它写成"已知未评估的代价"、
   明确不豁免，不写成"已评估为可接受"；现在评估做完，读数如实入档。执行中有两处偏离原计划，
   都在评估记录里写明：① 判据没用 `make redistill`（它是"整组替换"、会改写快照与库），改用等价的
   **只读配对脚本**（同一份 raw、同一批次划分、同一 prompt，唯一变量是 `thinking` 的真假）；
   ② 当初用来论证"必须做对照"的「同批 9 → 28 条」**没有被复现**（配对对照是 ON 24 / OFF 29，
   约 1.2 倍，不是 3 倍）。
2. **安全默认保留 `true`（关），不改。** 知道这是"质量换延迟"之后，"只对 ask 关"依然站得住：
   ask 是人在等且**有引用列表可核验**（人自己能判断答案有没有据），蒸馏是批处理、延迟不可感、
   质量优先。也就是说，这个交换的正确性由「只关 ask」这个**边界**保证，不由默认值本身保证。
   要补的是一句诚实说明：默认值是**延迟驱动**定下的，质量侧的对照欠着（见第 1 条）。
3. **状态**：Accepted，生效 2026-09-27；第 1 条的对照评估**已执行**（读数见「评估记录（T086）」节），
   定性已由用户于 2026-09-28 落笔（见「质量定性（2026-09-28 用户裁定）」节）——
   跟踪项 `tasks.md` **T086 已勾**。

## 评估记录（T086，2026-09-27，配对对照、只读）

**口径**：`make redistill` 是"整组替换"，跑它会改写快照与库；这条评估只要两臂的**读数**，
所以改用等价的一次性脚本做**纯内存配对对照** —— 同一份 `data/raw/2026-09-18.json`、
同一次 `split_for_batches` 批次划分、同一个 `distill_prompt.build_messages`、同一个模型
（`doubao-seed-2.1-lite`），**唯一变量是 `chat(..., thinking=)` 的真假**；不写快照、不入库。
`src/distill._llm_entries` 的重试语义照抄（非法 JSON 重问一次、未知类型纠正一次）。

**前置**：09-18 快照 8 条素材（LLM 素材 3 条、23.3 万字符 → 切 3 批：109898 / 123398 / 721 字符）；
第 3 批整批都是直并入素材，两臂都跳过（与 `distill` 一致，不白烧 token）。实际 **4 次** chat 调用。
三批中的前两批即 "batch0 / batch1"。

| 指标 | thinking ON（现状） | thinking OFF | 库里现有（历史产物，参照） |
|---|---|---|---|
| 条目数（去重后） | 24 | 29 | 27 |
| 熔断后（cap 30） | 24 | 29 | — |
| 类型分布 | error 11 / progress 8 / reflection 3 / idea 2 | error 12 / progress 10 / reflection 5 / idea 2 | progress 10 / error 9 / reflection 8 |
| 文本中位长 | 224 | 361 | — |
| 文本总长 | 8092 | 10080 | — |
| 文本分布 | <200 字 9 条 / ≥400 字 8 条 | <200 字 5 条 / ≥400 字 13 条 | — |
| 耗时 | 232.5s | 106.4s | — |
| 重试（非法 JSON / 未知类型） | 0 / 0 | 0 / 0 | — |

逐批：ON batch0 109898 字符 → 16 条 / 109.0s，batch1 123398 → 8 条 / 123.5s；
OFF batch0 → 13 条 / 51.1s，batch1 → 16 条 / 55.3s。

**能可靠归因的**（不随采样变化的读数）：

- **延迟**：232.5s → 106.4s（−54%），逐批同向。
- **JSON 有效性**：两臂重试均为 0 —— 关 thinking 没有把解析打坏。
- **条目数量级**：24 vs 29（≈1.2 倍），**不是**当初记的 9 → 28（3 倍）。

**不能可靠归因的**（同一 prompt、单次采样；两臂只差一个布尔值，但模型照样随机）：

- **条目内容与长度**。两臂各自都把部分事件**中英双写**（ON：T061 一条中文 + 一条英文；
  OFF：T061、T018 各一条中文 + 一条英文），所以"条目数"本身就被同事件的语言重复灌了水 ——
  两臂都有，不是哪一臂的病；语言构成也不同（ON 英文 8 / 24，OFF 英文 15 / 29）。
- 长度差异也**不是"全面变长"**：把两臂条目按**事件锚点**归类（29 个语言无关锚点）后，
  21 个事件两臂都覆盖、ON 独有 3 个、OFF 独有 5 个；共有事件里 **13 个 OFF 更长、8 个 ON 更长**，
  且方向有系统性 —— OFF 更长的是流程/工具/约定类（`prd-workflow` 门 +433 字符、sync 锁 +381、
  插件架构 +348、蒸馏上限 +345），ON 更长的是复盘/教训类（overclaim −625、Slicer 地图 −553、
  CI 算错 −468）。即：**两臂的差别在"把冗长分配给哪一类事件"，不在"信息量多少"。**

**本次对照的结论边界**：它足以**否掉**「OFF 会让蒸馏条目塌成 3 倍」（未复现），也足以说
「OFF 不破坏 JSON 有效性、延迟减半」；但**不足以为"质量可接受 / 不可接受"背书** ——
单日、单次采样，逐条差异与采样噪声不可分。要过这个判，需要每臂重复采样（≥3 次）看是否稳健，
或明确接受"以事件覆盖与类型分布为判据、忽略逐条差异"。

**原始产物**（一次性，未进仓库）：两臂各一行一条的 `{type, source, refs, text}`（`/tmp/t086/`），
分析脚本同为一次性。不固化进 `scripts/`：`redistill` 已是库里现成的替代（代价是它会写库），
而本条是一次性欠账、不随新日期重复需要。

## 质量定性（2026-09-28 用户裁定）

**用户 2026-09-28 指示按建议执行**，即采用 `notes/decision-sheet.md` 的倾向项
（1A + 2A；2A 的「9 → 28 未复现」订正已在 2026-09-27 落地）。

**结论：「已评估：无证据显示 OFF 有质量退化」** —— ADR-13 保持现状（只对 ask 关 thinking，
蒸馏继续开）。

**采用的判据**（这三条是本次对照里唯一不随采样漂移的读数）：

1. **事件覆盖**：29 个语言无关事件锚点里 21 个两臂都覆盖，ON 独有 3、OFF 独有 5；
2. **类型分布**：ON error 11 / progress 8 / reflection 3 / idea 2，OFF 12 / 10 / 5 / 2 —— 同构，无类型塌陷；
3. **JSON 有效性**：两臂非法 JSON 与未知类型的重试均为 0，关 thinking 没有把解析打坏。

**逐条文本差异不进判据**：长度、措辞与中英双写在两臂上都出现，方向虽有系统性
（OFF 长在流程/工具/约定类，ON 长在复盘/教训类），但单次采样下与噪声不可分 ——
故如实记为「不构成质量退化证据」，而不是「已证明两臂等价」。

**结论边界（未做、需知）**：

- 单日（09-18）、单次采样，**没有**每臂 ≥3 次的重复采样，因此判不了 run-to-run 方差；
- **延迟是本次唯一的强信号**（232.5s → 106.4s，−54%，逐批同向）——它是"可以关"的论据，
  不是"应该关"的论据；默认值仍是延迟驱动定下的。
- 若将来要更强的结论，杠杆是重复采样或换判据（decision-sheet 的 B/C/D 项），
  本轮用户选择不追加实验。
