# ADR-19 删除用**软删除 + 检索期过滤**，不做硬删除

- **状态**：Accepted（2026-09-28；用户授权按推荐值采用，记录见 `specs/001-learning-memory-rag/v08-decisions.md`）
- **日期**：2026-09-28
- **素材**：PRD v0.8.0 FR-029 / NFR-011；spec FR-027
- **实施位置**：`src/entries.py`（删除/恢复）、`src/ask.py` + `src/entries.py`（可见性过滤）、`src/api/app.py`

## 背景

页面上要能删掉"不该入库"的条目。删除在向量库里有两个层次的含义：**让人看不到**，和**真的不存在**。这两件事的成本与风险差一个量级。

## 备选与被否的理由

| 方案 | 为何没选 |
|---|---|
| **硬删除**（从 Qdrant 抹掉，甚至动 `data/raw/` 快照里的素材） | ① 不可恢复——误删就是误删；② 快照是重蒸馏的重放基线，动它会破坏 AC-009 与 ADR-14 的整套语义；③ 用户 2026-09-28 明确删除动机只有"内容错、冗余"这一半，**不涉及敏感内容**，所以"必须真抹掉"这个需求不存在 |
| **新增墓碑表** | 多一处存储与一致性维护；而"不可见"这一目的 payload 字段就能达到 |
| **软删除 + 检索期过滤**（采用） | 可恢复、ID 不变、重放行为明确（同 ID 保持删除态）；代价是每条查询要带一个条件 |

## 证据

- 过滤是本项目既有模式：`ask` 已经是"向量检索 + payload 过滤"（FR-018 / AC-004），加一个"不存在 `deleted_at`"的条件不引入新机制。
- 规模上：条目总量预期千级（plan Technical Context），过滤开销可忽略。

## 后果与可逆性

- **可逆性**：高。字段留着，删与恢复都是改一个 payload 键。
- **代价（如实记录）**：磁盘上仍存着文本——所以本 ADR **不构成"敏感内容已清除"的保证**。若将来有敏感内容诉求，需另立硬删除需求（连同 `data/raw/` 快照的处理）。
- **悬空边**：`related` 指向已删条目时，检索期忽略该边，**不级联删边**——级联会把可恢复性变成不可恢复（恢复后边没了）。
- **对账口径**：面向人的路径（列表、`ask`）一律排除已删；**只读诊断**（`rerun-overlap` / `batch-edges` / 重蒸馏 diff）**不过滤**并标注"已删"，否则"页面 90 条、工具说 95 条"会变成新的谜题。

## 决策

1. 删除 = 写 `deleted_at`（+ 可选 `deleted_reason`）；恢复 = 清掉它们。两者都递增 `rev`。
2. 面向人的读取带"`deleted_at` 为空"条件；页面提供"显示已删除"开关（默认关）作为恢复入口。
3. 重放时同 ID 的已删条目**保持删除状态**（不复活）。
4. 不做硬删除；不级联删边；诊断工具不过滤。
