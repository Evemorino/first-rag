# ADR-12 按**输出**切批：`distill.batch_max_chars`

- **状态**：**Accepted（2026-09-27 用户裁定）**（LG-005：结论由用户写，AI 只给素材与选项；
  问答清单与逐题答案见 `notes/decision-sheet.md`）
- **日期**：2026-09-26
- **素材**：`specs/001-learning-memory-rag/adr-candidates.md` 的 ADR-c2（AI 整理，2026-09-26）
- **实施位置**：`src/distill_batches.py:split_for_batches`、`src/distill.py` 按批调用、`config/schema.json` 的 `distill.batch_max_chars`（默认 120000）

## 背景

一次 `distill` 把当天全部素材塞进**一次** chat 往返时，方舟会以
`finish_reason='length'` 截断输出，`json.loads` 报 `Unterminated string`，
`_parse_or_retry` 的重试是**原样再发同一个 prompt**，于是注定再断一次 ——
一整天 0 条入库，还白烧 218 秒与一堆 token（README 有专节记这条）。

## 备选与被否的理由

| 方案 | 当时为何没选 |
|---|---|
| 加大 `max_tokens` | 无关：断的是**服务端 completion 上限**，不是请求参数。实测 `max_tokens=30` 也一样 |
| 靠 `_parse_or_retry` 重试 | 重试**原样再发**，同一处再断一次，整天 0 条入库 |
| 按素材**条数**切批 | 尺寸极不均（一条会话可达 200000 字符），字符数才是决定量 |
| 流式收输出再拼 JSON | 未走；解析半截 JSON 的成本没评估 |

## 证据

- 09-18 断在 **6894 字符 / 6865 completion tokens**、`finish_reason='length'`；
  而输入大 5.7 倍的 09-23（1.33M 字符）**一次就过** —— 决定成败的是**输出**长度，
  不是输入长度。这正是本条反直觉、值得留痕的地方。
- 修完同一天实测：188.06s、2 次 chat 往返、27 条入库、库内 39 点。

## 后果与可逆性

- **可逆性**：配置项，改 1 个数字。
- **副作用（要显式记进决策）**：切批后 `source_refs` 只能引用**本批**的素材
  （`src/distill.py`），跨批的关联在蒸馏期就断了 —— 同一事件分在相邻两批时，
  关联边要等库内相似度去补，蒸馏期看不出来。

## 决策

**用户 2026-09-27 裁定（LG-005：结论由用户写；问答清单见 `notes/decision-sheet.md`）。**

1. **`120000` 认，但如实记为经验值。** 仓库里没有它的推导过程；真正有实证的是**观察值**：
   实测失败的批次断在 ~6894 字符 / 6865 completion tokens，而输入大 5.7 倍的 09-23（1.33M 字符）
   一次就过 —— 决定成败的是**输出**长度。`batch_max_chars` 因此只是从输入侧间接压低单批输出的
   旋钮，120000 属于"宽到不会断"的一档，不是算出来的最优值。将来若要换数，依据应当是
   "单批输出 p99 距 completion 上限还剩多少余量"，而不是输入字符数本身。
2. **跨批关联断裂：记为已知副作用，并留一条观测项。** 边界写清：`source_refs` 只引用本批素材，
   同一事件分在相邻两批时蒸馏期即断链，只能等库内相似度补；而"库内能不能补回来"目前**没有
   观测数据**。这与 T084 裁定的「in-run 不连边」是两件事，不得互相归因。
   观测项：下次 `ingest` 后抽查一批"同一事件分两批"的样点，看是否长出跨运行边。（已登记为 `tasks.md` **T087**；2026-09-27 观测完成，结果见文末「观测记录」）
3. **状态**：Accepted，生效 2026-09-27。配置项，改一个数字即可回退。

## 观测记录（T087，2026-09-27，只读）

**样本**：全库 221 点。能重建批次归属的只有 09-25（54 点 / 18 批，`source_refs` 与当前快照 100% 对得上）；
09-24 的 87 点在当前快照里 `source_refs` **全部找不到**（快照已被窄 scope 重跑覆盖），只能归入 unknown-batch。

| 09-25 同日分组 | 对数 | ≥0.75 的对 | 其中有边 | max cos |
|---|---|---|---|---|
| 同一次运行 / 同一批 | 243 | 0 | 0 | 0.722 |
| 同一次运行 / **不同批** | 468 | **5** | **0** | **0.906** |
| 跨运行 | 720 | 8 | 8 | 0.804 |

1. **当次运行确实断链**：5 对跨批对（cos 0.765–0.906，批 1 ↔ 批 2）在 16:09:35 那次运行里
   **一条边都没有**；而同一批内 ≥0.75 的 0 对、跨运行 8 对**全部有边**。这不是"批数太多"的偶然，
   是 in-run 排除的直接后果。
2. **后来的运行能间接补回，但只有 2 / 5**：
   - 2 对（`a6f46751` ↔ `d4a11d68`、`95df12fc` ↔ `ed5c6ac1`）在 16:19:19 那次运行产出第三方条目后，
     两个成员各自连上**同一个**邻居（`17f31a82` cos 0.787 / 0.752；`7cbdb1a4` cos 0.782 / 0.771）
     → 形成 **2 跳路径**，不是直接连边。
   - 3 对**两侧至今一条边都没有**，包括相似度最高的那对（0.906：`926dbe2e` ↔ `997d1ee8`）。
3. **机制**：那 6 条补回边的 cos 全在 **0.752–0.810** —— 高于关联边阈值 0.75、**低于**新颖度阈值 0.82。
   即后续运行的近重复条目既躲过了 `filter_novel`、又够格建边。推论：**越像的跨批对越补不回来**
   （>0.82 会先被去重拦掉），最高那对至今孤立正是这个原因。
4. **附带发现**：快照损失（ADR-14）还有第二重后果 —— 它同时毁掉这条观测本身的可行性（09-24 无法重建批次）。

**对决策的影响**：不改变决策第 2 条（仍记已知副作用），但把"有没有观测数据"从**无**换成**有条件**：
能补回，但限于 0.75–0.82 的窄带、只以 2 跳形式出现、且不保证。若将来要直接边，杠杆仍在
ingest 侧的批内 / 跨批配对 —— 与 T084 否掉的方向是同一处 ★ 区。
