# 阶段详解

进入某个阶段时读取对应小节。每阶段含输入、动作、产物、退出条件与不通过时的处理。

## 阶段一：PRD 创建或更新

**输入**：用户需求、现有 PRD、相关反馈、项目背景。
**动作**：创建或修订 PRD，明确需求来源、范围、目标、用户场景、FR/NFR、AC、边界、非目标、依赖、风险与待澄清项。
**产物**：可追溯的 PRD 或 PRD 变更记录。
**退出条件**：需求范围和验收方向可供 spec 化；关键未知项被明确标识。
**不通过**：继续澄清，不进入 `specify`。

## 阶段二：specify

**输入**：PRD、项目 constitution、架构规范、相关历史工件。
**动作**：使用 `spec-kit` 将 PRD 转化为结构化 spec；每项关键能力关联 PRD 的 FR/NFR/AC ID。
**产物**：`spec.md`。
**退出条件**：spec 覆盖 PRD 的范围、用户场景、功能与验收，且未擅自扩张范围。
**不通过**：修订 spec 或回到 PRD 修订。

## 阶段三：clarify

**输入**：PRD、spec、相关项目上下文。
**动作**：解决影响实现、验收、兼容性、安全、性能、数据处理或异常行为的歧义。
**产物**：更新后的 PRD/spec，以及必要的决策记录。
**退出条件**：无影响后续决策的 `[NEEDS CLARIFICATION]`。
**不通过**：继续 clarify；如问题属于需求定义，先更新 PRD。

## 阶段四：grill-me（需求质询）

**输入**：PRD、spec、关键假设、边界、异常场景、验收标准。
**动作**：使用 `grill-me` 质询：

- 用户目标与真实业务问题是否一致；
- 范围、非目标和优先级是否明确；
- 正常流、边界流、异常流和失败处理是否完整；
- 隐含假设、外部依赖、权限、数据、兼容性与风险是否被识别；
- 验收标准是否可观察、可验证、可追溯。

**产物**：质询结论、问题清单、决策与通过/不通过状态。
**退出条件**：无阻塞性问题；关键假设、边界和验收可明确回答。
**不通过**：按问题归属回到 PRD、specify 或 clarify；修订后重新执行本阶段。

## 阶段五：checklist

**输入**：已通过需求质询的 PRD 与 spec。
**动作**：使用 `spec-kit` 生成并执行 checklist，检查完整性、一致性、可测试性和可验证性。
**产物**：`checklist.md`。
**退出条件**：所有必需检查项通过；未通过项已修订或有明确批准的例外。
**不通过**：回到 spec 或 PRD 修订；受影响时重新执行 `grill-me`。

## 阶段六：grill-with-docs（规格与文档审查）

**输入**：PRD、spec、checklist、项目文档、架构规范、代码上下文。
**动作**：使用 `grill-with-docs` 审查：

- PRD 与 spec 是否完整映射；
- spec 是否违反 constitution、架构约束、既有接口或项目文档；
- 是否有术语不一致、需求漂移、遗漏的依赖、不可验证表述或冲突；
- 现有实现对需求可行性、迁移、兼容性和风险的影响。

**产物**：文档审查结论、问题清单、关联工件和放行状态。
**退出条件**：无阻塞性冲突、漂移、遗漏或不可验证项。
**不通过**：根据问题归属回到 PRD、specify、clarify 或 checklist；修订后重新执行 `grill-with-docs`。

## 阶段七：plan

**输入**：通过审查的 PRD、spec、checklist、架构约束、现有代码上下文。
**动作**：使用 `spec-kit` 制定技术方案，覆盖架构、模块边界、接口、数据模型、错误处理、兼容性、迁移、测试策略、可观测性和风险。
**产物**：`plan.md`。
**退出条件**：Constitution Check 通过；方案完整映射 spec，且技术风险有处置策略。
**不通过**：修订 plan；若发现需求不可行或需求含义需改变，回到 PRD/spec。

## 阶段八：grill-with-docs（计划审查）

**输入**：PRD、spec、plan、项目文档、架构约束、现有实现。
**动作**：使用 `grill-with-docs` 检查技术方案与需求、项目规范和现状之间的一致性，特别检查：接口契约、数据兼容、迁移与回滚、权限安全、性能、测试策略和文档影响。
**产物**：计划审查结论。
**退出条件**：无阻塞设计冲突或未处理风险。
**不通过**：回到 plan；若问题源自 spec/PRD，则回到对应工件修订并重审。

## 阶段九：tasks

**输入**：PRD、spec、plan。
**动作**：使用 `spec-kit` 拆分可独立执行和验证的任务。每个任务必须关联相关的 `FR-*`、`NFR-*`、`AC-*` 或 `SC-*`，并注明代码位置、依赖、验证方式和完成定义。
**产物**：`tasks.md`。
**退出条件**：任务覆盖全部计划项；依赖顺序清楚；每项均有验收和验证方式。
**不通过**：修订 tasks 或 plan。

## 阶段十：grill-me（任务与实施前质询）

**输入**：PRD、spec、plan、tasks、验收标准和风险项。
**动作**：使用 `grill-me` 质询：

- 每项任务是否有清晰的输入、输出、边界和完成定义；
- 是否遗漏异常路径、回滚、兼容性、权限、数据迁移或观测需求；
- 任务排序是否符合依赖；
- 是否存在无法验证的任务或验收标准；
- 是否有未落入任务的 PRD/spec/plan 要求。

**产物**：任务质询结论。
**退出条件**：任务可执行、可验证、可追溯，无阻塞性遗漏。
**不通过**：通常回到 tasks；涉及设计则回 plan；涉及需求则回 PRD/spec；修订后重新质询。

## 阶段十一：analyze

**输入**：PRD、spec、plan、tasks、两类审查结论。
**动作**：使用 `spec-kit` 分析一致性、覆盖度、依赖、风险、重复任务、任务顺序和验收闭环。
**产物**：`analysis.md` 或等价分析报告。
**退出条件**：无 CRITICAL 问题；HIGH 问题已修复或有明确、可接受的处置决定。
**不通过**：按问题归属回到 PRD、spec、plan 或 tasks；之后重新执行受影响的审查和 analyze。

## 阶段十二：implement

**输入**：已通过 analyze 的 tasks、plan、spec 与 PRD。
**动作**：按 tasks 实施；按需使用非流程类 `superpowers` 支持测试驱动开发、调试和完成前验证。同步更新任务状态、测试、必要的文档与实现证据。
**产物**：代码、测试、验证记录、更新后的任务状态与相关文档。
**退出条件**：任务完成定义满足；验证有证据；无未处理的阻塞缺陷。
**不通过**：留在 implement 修复并重新验证。若发现需求、规格或方案错误，按变更控制回退。

## 阶段十三：converge

**输入**：PRD、spec、plan、tasks、analysis、代码、测试、文档和验证证据。
**动作**：使用 `spec-kit` 或项目约定方式收敛状态：同步已实现范围、任务完成状态、已知限制、验证结果和文档变更。
**产物**：收敛记录、更新后的工件与交付摘要。
**退出条件**：所有工件对同一交付范围表达一致；未完成项明确记录并获得处理决定。
**不通过**：回到对应工件或 implement 修订。

## 阶段十四：grill-with-docs（最终一致性审查）

**输入**：最终 PRD、spec、plan、tasks、实现、测试、项目文档与收敛记录。
**动作**：使用 `grill-with-docs` 核对交付是否与 PRD 的范围、FR/NFR、验收标准和非目标一致，核对文档、任务状态、测试和实现之间是否存在漂移。
**产物**：最终审查结论。
**退出条件**：无未处理缺口；交付可标记为 `Converged`。
**不通过**：按问题归属回退到 PRD、spec、plan、tasks 或 implement；重新执行受影响的分析、验证与最终审查。

## 问题记录格式

每个问题至少记录：

- 问题 ID；
- 严重级别：CRITICAL / HIGH / MEDIUM / LOW；
- 问题描述与证据；
- 受影响的 PRD/spec/plan/tasks/实现条目；
- 建议回退阶段；
- 处理决定、负责人或后续计划；
- 复审结果。
